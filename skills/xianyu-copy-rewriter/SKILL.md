# 闲鱼商品文案重写

## 目标与输入

把原始商品信息整理成可供卖家审核使用的**一个新标题和一份完整商品描述**：让买家认清商品、理解购买价值，同时知道实际能收到什么、怎样获取、使用有什么条件。

- 输入至少有原商品标题与描述，可附已核实事实、本次经营安排、商品编号及风格要求。
- 仅有原文也直接起草；不因缺少价格、目标人群或非关键说明而反复提问。确实无法识别卖什么时，只问必要问题。
- 默认中文、真实个人卖家语气、短句分段。尊重用户指定的长度和格式，不强制三版标题、固定六段式或营销报告。
- 只重写文字；不抓取、定价、发布、发货或调用外部服务，不宣称通过平台审核或保证成交。

## 先读取经营规则

每次执行先读取 [本店经营与说明规则](../../business/rules/xianyu-shop-operations.md)，它是交付、网络资料收费性质和侵权反馈说明的统一来源。路径相对本文件；仅在此项目的适用场景使用这些默认安排。

原商品提供商品事实，本店规则提供适用的经营安排，本次用户明确的事实更正和商品安排优先。**原卖家的条款不自动成为本店承诺。** 规则文件不可访问时，不凭记忆补齐本店安排；仍可基于原文起草，并在有实质影响时单列需确认事项。

## 1. 提取商品与服务信息

内部完成下表，不默认向用户展示分析。每项区分“原文陈述”“本次核实或更正”“本店规则”“缺失或矛盾”，使最终表述能追溯来源。

| 提取项 | 要回答的问题 | 常见误判 |
| --- | --- | --- |
| 商品身份与形态 | 买的是资料文件、录播教程、模板、软件使用权、源码，还是实际服务？ | 源码包写成即开即用的软件；教程写成代做服务 |
| 交付物与范围 | 实际拿到哪些文件、模块、格式、版本或服务成果？哪些明确不包含？ | 根据品类补课程目录、赠品或数量 |
| 内容与功能 | 教什么、包含什么，或工具实际能做什么？ | 把“讲解自动化”写成“自动完成任务” |
| 使用价值与人群 | 哪个真实特征解决哪种具体麻烦？谁适合、谁不适合？ | 一律“新手友好”“任何人都能用” |
| 使用门槛与成本 | 需要什么设备、软件、版本、账号、会员、API、基础或额外支出？ | 可下载等于能运行；提供源码等于包部署 |
| 服务内容与边界 | 咨询、安装、部署、定制、教学、更新是否属于购买内容？范围或期限是什么？ | 原卖家说“免费安装”就替本店承诺 |
| 交易与权利说明 | 如何交付、是否有适用限制、来源署名或授权说明？ | 网盘交付当核心功能；整理费当授权证明 |

### 提取与取舍

- 一般商品内容、功能、参数可忠实改述，不自动当成第三方核验结果。明确事实、数量、版本和有购买意义的限制应保留，不能因不利营销就删去。
- 区分“商品自带的服务权益”和“原卖家个人提供的附加服务”。前者需有适用于本商品的依据；后者未经本店确认，不写成承诺。原文无法区分而又影响购买时，记录卖家审核项，不静默删除。
- 原文自称原创、亲测、官方授权、有客户案例，不能直接转换为本店的第一人称经历或资质。
- 清理重复、空话和无关口号；版权、使用条件、额外费用、交付限制等先判断含义再处理，不能作为“无关声明”一并删掉。
- 不照搬原卖家网盘链接、联系方式、店铺身份或引流话术。按本店规则处理领取说明，不代替商品履约。

## 2. 从真实信息形成购买理由

先确定一个主要购买理由，再选择少量支撑信息。可从痛点、具体内容、省去的步骤、适用场景或交付成果切入，不机械要求每条都有同样数量的钩子。

**表达链路：具体内容或能力 → 使用场景 → 有依据的买家利益。**

- “包含按主题分类的选品与上架资料”可表达为“不用在零散内容里来回找，按主题查看选品和上架方法”。
- “提供剪辑源码”不能扩写成“无需配置、一键生成视频”；“提供操作教程”不能扩写成“有人带着做”。
- 不只罗列“功能丰富、实用、保姆级”；让买家知道具体多了什么、少了什么麻烦。也不必把每个事实硬凑成一条利益。
- 原文有吸引力且有依据的表达应保留或改善；缺乏依据的结果承诺，用实际可提供内容替代，避免把整条文案改成泛泛的“欢迎咨询”。

需要选择营销角度时参考 [营销钩子速查](references/marketing-hooks.md)。

## 3. 写标题与营销正文

### 标题

- 商品核心搜索词在前，明确品类，再加最有说服力的 1–2 个真实内容、价值或场景。
- 不把“秒发、网盘、付款自动发送”放进标题；售卖自动发货功能服务时按功能处理。
- 通常约 18–30 个汉字，自然清楚优先，遵守本次用户的具体限制，不宣称平台强制规格。
- 不堆无关搜索词、夸张情绪、表情或没有证据的数量和承诺。

### 正文

根据商品组织，避免固定模板感：

1. 开头用最贴切的场景、需求或具体价值吸引注意，尽早说明卖的是什么。无需每条都以“想……但不会……？”开头。
2. 讲清实际内容或功能，挑出最有购买意义的部分，必要时用少量列表呈现。内容清单与卖点避免重复抄一遍。
3. 交代适用人群和关键条件。付费依赖、不含部署、版本限制等，靠近相关功能说明，不能用“新手友好”掩盖。
4. 依商品选择自然收尾。信息明确、可自动交付的资料无需强制先咨询；需要确认需求、环境或服务范围时，再引导拍前沟通。

像懂商品的卖家讲话：一段通常 1–2 句，信息密集时分点，少量使用 `✅` 等标记。避免“赋能、颠覆、闭眼冲、无脑入”、连续感叹号、同义反复和整屏符号。信息少则短写，内容多则合理展开，不为凑字数删必要条件。

## 4. 组合适用的商品说明

按 [经营规则](../../business/rules/xianyu-shop-operations.md) 选择本商品适用项，在描述末尾形成简短“商品说明”；具体措辞、适用范围与未确认安排以该文件为准，不另维护一套默认条款。

- **交付与领取**：可走网盘的数字文件采用本店自动网盘交付规则，即使原文没有写也应补齐；实际服务不套用自动完成履约。
- **使用与服务边界**：补全已知且尚未在正文说清的依赖、范围、费用或限制。不重复长段功能，也不猜未知环境和售后政策。
- **资料来源、费用性质与权利说明**：网络采集整理类商品选用对应说明；原创商品、软件授权或技术服务不机械套用。
- 未确认的安排放卖家备注，不把“待核实”“发布前需确认”混入买家描述。无适用说明时可以省略该小节。

交付是辅助信息。只有售卖的商品本身就是自动发货功能时，才把自动发货写为核心卖点。

## 5. 事实与承诺的边界

- 不编造功能、赠品、销量、评价、授权、价格、折扣、库存、使用经历或售后；不改动重要费用和适用条件。
- 收益数字、成功率、包过、永久稳定、无限使用、无额外费用、时效保证等，不能仅因原文出现就变成确定承诺；需有明确核实依据且不误导。没有依据时改写为具体内容或机制，必要时记入卖家备注。
- 不用“别人做到”“案例拆解”包装未经核实的收益数字，也不保证学习、使用或申请的结果。
- 版权声明按经营规则处理，不据此断言有销售授权、不会侵权或平台允许发布。
- 在原文冲突时优先采用有依据的具体事实，不用强卖点掩盖矛盾。仅在无法起草有效文案时才提必要问题。

## 6. 交付前静默检查

- 买家能否辨认商品形态，以及实际包含、不包含什么？有没有把教程、源码、工具和服务相互混淆？
- 是否提取了关键功能和服务边界，而非只剩通用宣传语？价值表达是否有具体事实支撑？
- 使用门槛、付费依赖、版本和重要限制是否保留？有没有误继承原卖家服务？
- 本店适用的交付说明是否完整？网络来源与收费说明是否只用于适用品类？
- 标题和主要卖点是否围绕商品价值？有没有虚构数字、效果、权限或退款安排？
- 买家描述与卖家审核备注是否分开？正文是否自然、简洁、不重复？

检查不默认展示，也不输出“合规通过／可发布”等未经验证的结论。

## 输出与批量规则

默认只交付结果，不展示提取表或营销分析：

```text
标题：<新标题>

商品描述：
<自然开头，尽早明确商品身份>

<具体内容、功能、购买价值与必要条件，按商品灵活组织>

商品说明：
<适用的交付、使用及资料来源等说明>
```

- 若有影响购买决定的缺失、冲突或未经确认的承诺，在完整描述之外单列 `卖家审核备注（不属于商品描述）：`，仅列本商品需要处理的具体事项；没有则省略。
- 结构化输出时遵守用户或工作流契约。`title` 与 `description` 仅放买家文案；工作流允许 `metadata` 时，审核事项可放在 `metadata.review_notes`，不得混入 `description`。不要擅自更改现有接口字段。
- 多条商品按输入编号和顺序逐条输出，逐条判断说明的适用范围。完全重复也不静默删记录；仅用户要求去重时合并并提供映射。
- 商品或运行 ID 等输入标识按下游要求保留。仅要标题或描述时按要求输出，不额外附加其他主要结果。

需要对照成品或判断边界时，读取 [改写示例](references/examples.md)，重点检查资料、软件和服务的差异；示例事实不能移植到其他商品。
